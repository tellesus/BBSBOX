# M12 maintenance primitives

Implementation reference, not scope authority. Follow the maintained [M12 brief](../../docs/development/modules/M12-maintenance-recovery.md) and current user instructions. Foundation-node storage/configuration backup and isolated restore pass actual Debian lifecycle checks. A worker checkpoint provider has local fixtures; a complete game-node snapshot/restore profile, M11 transport, release verification, scheduling/retention and restored signing activation remain open.

## Protected archive v1

`archive::seal` inventories an immutable private staging tree, signs the inventory using the node key, and streams an uncompressed USTAR archive through age X25519 recipient encryption. The backup recipient is a separate operator key; its secret need not be present during encryption. Neither a person key nor a client recovery kit is exported through this API. Callers must first prepare a consistent snapshot and select its required configuration and secret files.

Pinned dependencies are age 0.12.1 and tar 0.4.46 with default features disabled. The format follows [age v1.1.0](https://c2sp.org/age@v1.1.0); application signing uses [RFC 9864 Ed25519 algorithm -19](https://www.rfc-editor.org/rfc/rfc9864.html). Public conformance bytes are in [archive-inventory-v1.json](../../protocol/fixtures/archive-inventory-v1.json), independently verified by [Node tooling](../../tools/verify_archive_vectors.mjs). The fixture seed is public test material.

The first tar entry is `inventory.cose`; subsequent regular files are exactly `files/<signed path>`, in inventory order. Headers use USTAR layout, with tar's binary numeric encoding for sizes beyond its octal field. No link, sparse, device, PAX or GNU extension entries are accepted. Source names are portable ASCII relative paths of at most 94 bytes, with no traversal, empty components or reserved device names. Empty directories are omitted. Every file has its size and SHA-256 hash recorded; export checks them again while streaming. Output uses a fresh destination and a private temporary file, finalized only after the encryption stream and file are synchronized. The staging tree and its ancestors must remain private and immutable throughout; this API does not provide filesystem isolation against an owner concurrently replacing paths.

The signed payload is compact UTF-8 JSON with exact field order: `format`, `node`, `archive`, `created_at`, `incarnation`, `files`; file records use `path`, `size`, `sha256`. Identifiers/hashes use lowercase hexadecimal, incarnation is a 16-integer byte array, time is a signed 64-bit integer, and file sizes are unsigned 64-bit integers. Unknown fields, alternate serialization and unsorted/duplicate paths are rejected. COSE_Sign1 is an untagged canonical four-element array, protected headers are `{1:-19,4:public-key-bytes}`, unprotected headers are empty, and external AAD is `bbsbox.archive-inventory/v1`. The inventory ID is SHA-256 of the complete COSE bytes. The nonzero random archive ID and signer incarnation identify the export; they confer no event, courier-credit or release-signing authority.

`archive::open` requires the expected NodeId and operator decryption key. It verifies the inventory before creating its fresh private output directory, then writes only listed regular files below `content/`. All sizes/hashes and the entire encrypted stream through its final authentication tag must verify. Parsing is bounded before generic CBOR/JSON/age processing; the age header is limited to 64 KiB with 1,024-byte lines. Extra members/data and truncated streams fail. On Unix, directories are private 0700 and files 0600, subject to a more restrictive umask.

An output is complete only when `inventory.cose` exists and `.archive-incomplete` is absent. Interrupted or failed extraction is disposable staging and must never be activated. Opening an archive alone does not run database migrations or create a writer. M12's coordinator must validate the full snapshot contents and use M02's recovery-blocked fresh restore; continuation policy remains a separate prerequisite to activation.

Default defensive ceilings: 50,128 files, 8 MiB signed JSON payload, 1 TiB per member and 8 TiB total content. These are parser limits, not supported appliance capacity claims. Callers may lower them. Export/import require available space for their bounded output plus a 32 MiB control reserve; concurrent disk consumption can still fail an operation. There is no compression or generic tar unpacking. Existing output is never replaced.

## Verification and next integration

`cargo test --locked --offline -p bbsbox-maintenance` covers a real SQLite/blob snapshot round trip across encryption chunks, canonical inventory vectors, wrong node/key, corruption, missing final tags, appended data, unsafe paths, links and duplicate entries. Unix CI additionally checks source symlinks and output modes. The independent vector tool checks exact bytes, node identity, signature/domain separation and the signed i64 boundary without rounding it through JavaScript numbers.

Dependency metadata for all 99 newly locked registry packages has a license expression; available choices include MIT, Apache-2.0, BSD, Unicode-3.0 and Unlicense. Selecting and bundling actual matching notices/source is still part of M12 release work; the development archive primitive is not a completed release bundle.

## Foundation-node capture and isolated restore

`snapshot::capture` runs inside a drained C01 maintenance callback while the caller holds configuration exclusion. It requires the existing expected node, captures a real SQLite/blob snapshot, checks the exact registered migration SQL hashes and copies bounded configuration/server secrets. Configuration is inventoried before and after copying; changed bytes/additions/deletions fail. The transient renewal lock is excluded before reads, including on Windows. Required configuration includes installation/node records, CA/key and caller-declared active certificate/key paths. Private staging must remain immutable through encryption.

The canonical `snapshot.json` descriptor uses `bbsbox.foundation-node-snapshot/v1`, node identity, snapshot time, sorted configuration file size/hash records, sorted required paths and an empty `game_checkpoints` list. This profile covers the current runtime with no installed games; it rejects claimed game checkpoints. Its runtime consumer accepts only the current identity/events migration owners; adding an owner requires extending/verifying the profile before export/restore can proceed. Configuration allows at most 120 files, 1 MiB per file and 8 MiB total; paths must also fit the outer inventory's bound after prefixing. Configuration/descriptor space is checked and allocated before core snapshot admission. A signed arbitrary tree or core-only copy never qualifies. Game checkpoints need coordinated integration before a games-enabled node can claim a complete backup.

Restore rechecks every authenticated staged file, core/blob integrity, exact compiled module registry, inner node-key consistency and all required configuration. It rejects extra members even when they carry a valid node signature. Output is a fresh private directory with `data/` and `configuration/`; the M02 database recovery marker is written before its data, and `.restore-incomplete` remains until copying/verifying/synchronizing finishes. `recovery.json` records the source inventory/time and unreconciled post-snapshot writes. Configuration is staged, never installed. Read-only identity inspection works without activating a signer; both signer startup and the writer still reject recovery-marked storage.

The [runtime operator commands](../node-runtime/README.md#local-maintenance-commands) consume this layer using the actual compiled migration registry. The [Debian helper](../../deploy/backup_development.py) stops/drains the real service, retains a private root-owned staging area for CA secrets, then restores only known SQLite/lock file ownership and resumes a previously active service. Actual guest backup, private ownership, source resumption after failure, inactive-source preservation, isolated restore, CA continuity and later reboot/network checks pass [CI](https://github.com/tellesus/BBSBOX/actions/runs/41375010768). Next: the combined game-node profile and restore, recovery continuation policy, offline release/update trust and retention automation.

## Worker checkpoint provider

`checkpoints::with_checkpoints` runs after core admission/drain with configuration exclusion retained. Its independent installed-game list must match the trusted registrations exactly, including disabled games retaining state; missing/duplicate/unsafe registrations fail before pausing. Registrations supply game handles, their separate nonoverlapping state roots and bounded local worker adapters. A fresh request fences every pause/checkpoint/resume operation. All workers pause/drain before any checkpoint is read; a partially failed pause still receives an idempotent resume attempt.

Workers return a request-bound durable checkpoint ID, positive state schema, implementation version and immutable checkpoint directory below their registered root. The coordinator rejects stale tickets, outside/symlinked sources, empty checkpoints and unsafe paths. It hashes/copies checkpoints into private staging with aggregate file/byte budgets, verifies source stability, then calls the publisher. The publisher must capture core/jobs and durably publish the combined signed inventory before returning success. Every attempted worker receives resume after success, failure or caught panic. One failed/panicking resume does not skip others; `CheckpointResumeFailed` returns the request and affected game handles for retry/attention.

Current internal limits: at most 64 registrations, safe single-component game handles up to 32 bytes, checkpoint/version labels up to 128 ASCII graphic bytes, and the archive's aggregate file/member/total/path bounds. These are provider bounds, not an appliance capacity matrix or a game HTTP wire format. M11 owns real authenticated worker IPC, command draining, fenced pause/lease release and game-state compatibility checks.

Five local tests use independent real worker SQLite databases. Under the actual core writer maintenance barrier, two worker checkpoints plus core pending jobs/receipts are signed/encrypted and reopened; replay of an already applied pending reward stays deduplicated. Other cases cover missing/duplicate registrations, shared budgets, partial pauses, stale/outside checkpoints, publisher failure/panic and failed/panicking resume. The current CLI foundation profile still rejects games. This provider alone does not launch games or establish a complete games-enabled node restore.
