# M12 maintenance primitives

Implementation reference, not scope authority. Follow the maintained [M12 brief](../../docs/development/modules/M12-maintenance-recovery.md) and current user instructions. Foundation/game-node backup/isolated restore and worker checkpoint collection pass Linux checks. Release authentication/payload/profile providers pass Linux checks. Offline installation/update, M11 transport/activation integration, scheduling/retention and restored signing activation remain open.

## Protected archive v1

`archive::seal` inventories an immutable private staging tree, signs the inventory using the node key, and streams an uncompressed USTAR archive through age X25519 recipient encryption. The backup recipient is a separate operator key; its secret need not be present during encryption. Neither a person key nor a client recovery kit is exported through this API. Callers must first prepare a consistent snapshot and select its required configuration and secret files.

Pinned dependencies are age 0.12.1 and tar 0.4.46 with default features disabled. The format follows [age v1.1.0](https://c2sp.org/age@v1.1.0); application signing uses [RFC 9864 Ed25519 algorithm -19](https://www.rfc-editor.org/rfc/rfc9864.html). Public conformance bytes are in [archive-inventory-v1.json](../../protocol/fixtures/archive-inventory-v1.json), independently verified by [Node tooling](../../tools/verify_archive_vectors.mjs). The fixture seed is public test material.

The first tar entry is `inventory.cose`; subsequent regular files are exactly `files/<signed path>`, in inventory order. Headers use USTAR layout, with tar's binary numeric encoding for sizes beyond its octal field. No link, sparse, device, PAX or GNU extension entries are accepted. Source names are portable ASCII relative paths of at most 94 bytes, with no traversal, empty components or reserved device names. Empty directories are omitted. Every file has its size and SHA-256 hash recorded; export checks them again while streaming. Output uses a fresh destination and a private temporary file, finalized only after the encryption stream and file are synchronized. The staging tree and its ancestors must remain private and immutable throughout; this API does not provide filesystem isolation against an owner concurrently replacing paths.

The signed payload is compact UTF-8 JSON with exact field order: `format`, `node`, `archive`, `created_at`, `incarnation`, `files`; file records use `path`, `size`, `sha256`. Identifiers/hashes use lowercase hexadecimal, incarnation is a 16-integer byte array, time is a signed 64-bit integer, and file sizes are unsigned 64-bit integers. Unknown fields, alternate serialization and unsorted/duplicate paths are rejected. COSE_Sign1 is an untagged canonical four-element array, protected headers are `{1:-19,4:public-key-bytes}`, unprotected headers are empty, and external AAD is `bbsbox.archive-inventory/v1`. The inventory ID is SHA-256 of the complete COSE bytes. The nonzero random archive ID and signer incarnation identify the export; they confer no event, courier-credit or release-signing authority.

`archive::open` requires the expected NodeId and operator decryption key. It verifies the inventory before creating its fresh private output directory, then writes only listed regular files below `content/`. All sizes/hashes and the entire encrypted stream through its final authentication tag must verify. Parsing is bounded before generic CBOR/JSON/age processing; the age header is limited to 64 KiB with 1,024-byte lines. Extra members/data and truncated streams fail. On Unix, directories are private 0700 and files 0600, subject to a more restrictive umask.

An output is complete only when `inventory.cose` exists and `.archive-incomplete` is absent. Interrupted or failed extraction is disposable staging and must never be activated. Opening an archive alone does not run database migrations or create a writer. M12's coordinator must validate the full snapshot contents and use M02's recovery-blocked fresh restore; continuation policy remains a separate prerequisite to activation.

Default defensive ceilings: 50,128 files, 8 MiB signed JSON payload, 1 TiB per member and 8 TiB total content. These are parser limits, not supported appliance capacity claims. Callers may lower them. Export/import require available space for their bounded output plus a 32 MiB control reserve; concurrent disk consumption can still fail an operation. There is no compression or generic tar unpacking. Existing output is never replaced.

## Verification and next integration

`cargo test --locked --offline -p bbsbox-maintenance` covers a real SQLite/blob snapshot round trip across encryption chunks, canonical inventory vectors, wrong node/key, corruption, missing final tags, appended data, unsafe paths, links and duplicate entries. Unix CI additionally checks source symlinks and output modes. The independent vector tool checks exact bytes, node identity, signature/domain separation and the signed i64 boundary without rounding it through JavaScript numbers.

Dependency metadata for all 99 newly locked registry packages has a license expression; available choices include MIT, Apache-2.0, BSD, Unicode-3.0 and Unlicense. Selecting and bundling actual matching notices/source is still part of M12 release work; the development archive primitive is not a completed release bundle.

## Foundation-node capture and isolated restore

`snapshot::capture` runs inside a drained C01 maintenance callback while the caller holds configuration exclusion. It requires the existing expected node, captures a real SQLite/blob snapshot, checks the exact registered migration SQL hashes and copies bounded configuration/server secrets. Configuration is inventoried before and after copying; changed bytes/additions/deletions fail. The transient renewal lock is excluded before reads, including on Windows. Required configuration includes installation/node records, CA/key and caller-declared active certificate/key paths. Private staging must remain immutable through encryption.

The canonical `snapshot.json` descriptor uses `bbsbox.foundation-node-snapshot/v1`, node identity, snapshot time, sorted configuration file size/hash records, sorted required paths and an empty `game_checkpoints` list. This profile covers the current runtime with no installed games; it rejects claimed game checkpoints. Its runtime consumer accepts only the current identity/events migration owners; adding an owner requires extending/verifying the profile before export/restore can proceed. Configuration allows at most 120 files, 1 MiB per file and 8 MiB total; paths must also fit the outer inventory's bound after prefixing. Configuration/descriptor space is checked and allocated before core snapshot admission. A signed arbitrary tree or core-only copy never qualifies. Game checkpoints need coordinated integration before a games-enabled node can claim a complete backup.

Restore rechecks every authenticated staged file, core/blob integrity, exact compiled module registry, inner node-key consistency and all required configuration. It rejects extra members even when they carry a valid node signature. Output is a fresh private directory with `data/` and `configuration/`; the M02 database recovery marker is written before its data, and `.restore-incomplete` remains until copying/verifying/synchronizing finishes. `recovery.json` records the source inventory/time and unreconciled post-snapshot writes. Configuration is staged, never installed. Read-only identity inspection works without activating a signer; both signer startup and the writer still reject recovery-marked storage.

The [runtime operator commands](../node-runtime/README.md#local-maintenance-commands) consume this layer using the actual compiled migration registry. The [Debian helper](../../deploy/backup_development.py) stops/drains the real service, retains a private root-owned staging area for CA secrets, then restores only known SQLite/lock file ownership and resumes a previously active service. Actual guest backup, private ownership, source resumption after failure, inactive-source preservation, isolated restore, CA continuity and later reboot/network checks pass [CI](https://github.com/tellesus/BBSBOX/actions/runs/41375010768). The game-node provider below extends this profile; recovery continuation, offline installation/update and retention automation remain open.

## Worker checkpoint provider

`checkpoints::with_checkpoints` runs after core admission/drain with configuration exclusion retained. Its independent installed-game list must match the trusted registrations exactly, including disabled games retaining state; missing/duplicate/unsafe registrations fail before pausing. Registrations supply game handles, their separate nonoverlapping state roots and bounded local worker adapters. A fresh request fences every pause/checkpoint/resume operation. All workers pause/drain before any checkpoint is read; a partially failed pause still receives an idempotent resume attempt.

Workers return a request-bound durable checkpoint ID, positive state schema, implementation version and immutable checkpoint directory below their registered root. The coordinator rejects stale tickets, outside/symlinked sources, empty checkpoints and unsafe paths. It hashes/copies checkpoints into private staging with aggregate file/byte budgets, verifies source stability, then calls the publisher. The publisher must capture core/jobs and durably publish the combined signed inventory before returning success. Every attempted worker receives resume after success, failure or caught panic. One failed/panicking resume does not skip others; `CheckpointResumeFailed` returns the request and affected game handles for retry/attention.

Current internal limits: at most 64 registrations, safe single-component game handles up to 32 bytes, checkpoint/version labels up to 128 ASCII graphic bytes, and the archive's aggregate file/member/total/path bounds. These are provider bounds, not an appliance capacity matrix or a game HTTP wire format. M11 owns real authenticated worker IPC, command draining, fenced pause/lease release and game-state compatibility checks.

Five tests use independent real worker SQLite databases. Under the actual core writer maintenance barrier, two worker checkpoints plus core pending jobs/receipts are signed/encrypted and reopened; replay of an already applied pending reward stays deduplicated. Missing/duplicate registrations, shared budgets, partial pauses, stale/outside checkpoints, publisher failure/panic and failed/panicking resume pass [Linux CI](https://github.com/tellesus/BBSBOX/actions/runs/41376302646). The current CLI foundation profile still rejects games. The game-node provider below owns combined restore; actual game launch/transport remains M11 work.

## Game-node snapshot profile

`game_snapshot::capture_and_seal` consumes the worker provider under the same drained core/configuration barrier, captures the verified foundation state, and assembles one `bbsbox.node-snapshot/v1` archive. Workers remain paused through validation and durable encrypted publication. The descriptor retains the foundation field order while binding a sorted nonempty `game_checkpoints` ID set. A separate canonical compact `game-checkpoints.json` contains sorted checkpoint records: game ID, common nonzero request, checkpoint ID, state schema, worker version and sorted file size/hash inventory. This index is limited to 8 MiB; the descriptor remains limited to 64 KiB. Both files and every game member are authenticated by the unchanged archive-inventory v1 signature. The existing foundation profile/format remains unchanged.

Trusted installed-package requirements independently specify each expected game ID, exact worker implementation version and exact state schema. Capture and restore require an exact set match, including retained disabled-game state; unknown/missing games and incompatible worker/schema versions fail. This first provider does not infer upgrade compatibility. M11 owns the real package/transport adapter and any later game migrations.

Verification checks the complete archive member set against core/blob, configuration and game catalogues. It rejects extra signed members, duplicate/unsorted metadata, mixed request fences, unsafe paths, wrong file commitments and noncanonical catalogues. Restore writes fresh private `data/`, `configuration/` and `games/<id>/` trees plus `recovery.json` and `game-recovery.json`. The outer incomplete marker remains until all game files are copied/verified/synchronized; the core recovery block remains afterward. No service, worker or signer is started. Matching game bytes and metadata are staged; actual game-engine validation/activation remains the consumer's responsibility.

Five tests use the real core maintenance writer and independent SQLite workers. They round-trip both games, core blobs, configuration and pending work, preserve deduplication, keep recovered writers blocked, reject missing/mismatched producers/packages and reject validly node-signed malformed/oversized catalogues or unregistered files. These and the foundation/worker failure suites pass [Linux CI](https://github.com/tellesus/BBSBOX/actions/runs/41381937859). The installed CLI still selects the foundation-only profile until M11 integrates its real registry/worker adapter.

## Release-manifest authentication v1

`release::verify_manifest` authenticates exact manifest bytes against a separately supplied trusted release public key. It does not inspect payload files, validate compatibility claims, persist sequence/key policy or permit installation. No production release key or installable signed bundle is created by the fixtures. The release signer keeps its secret separate from node/person/backup keys; its seed and signing key zeroize on drop and expose no Debug/Clone implementation.

The canonical compact JSON payload has fixed field order: `format`, `issuer`, `sequence`, `version`, `target`, `created_at`, `source_commit`, `core_schema`, `readable_core_schemas`, `module_migrations`, `files`, `next_key`. Domain/external AAD is `bbsbox.release-manifest/v1`; COSE uses the archive's canonical untagged Sign1 shape and fully specified Ed25519 algorithm -19. A release ID hashes the complete COSE bytes. The authority ID is `release-key:` plus SHA-256 of `bbsbox.release-signing-key/v1\0` and its public key; node IDs grant no release authority. A next-key declaration must be signed by the currently trusted key, and merely declaring it never changes installed trust.

Sequence is a nonzero u64, timestamp an i64, source commit 40 lowercase hexadecimal characters, and target exactly `debian13-amd64`. Version is 1–64 ASCII alphanumeric or `._-+` bytes. Core schema is positive; the sorted unique readable-schema list has 1–16 positive entries and includes it. Module migration records (`module`, `version`, `sha256`) are sorted by module/version, contiguous from 1 per module, at most 512 entries, and commit to exact SQL bytes. Future compatibility checking must compare these declarations against the actual compiled/runtime registry.

The payload is at most 64 KiB, with 9–128 sorted unique file records using archive path/hash rules, at most 2 GiB per member and 4 GiB total. Nonempty required files are the binary, unit, example configuration, project license/index and both selected license texts, plus `materials/source.tar`, `materials/dependencies.tar` and `materials/notices.json`. Presence in a signed manifest alone does not prove material completeness or matching contents. These are defensive initial profile bounds, not a capacity promise. Unknown fields, alternate encodings, malformed envelopes, weak/wrong keys, signature/domain mismatch and missing required entries fail.

[Public vector](../../protocol/fixtures/release-manifest-v1.json) bytes are reproduced in Rust and independently checked by [Node/OpenSSL](../../tools/verify_release_vectors.mjs), including u64/i64 boundaries without JavaScript rounding. Five tests cover canonical bytes, wrong authority/domain, tampering, key declarations, malformed/bounded inputs, required materials and invalid migration/path claims. Next: payload/material verification and compiled compatibility, then durable trust/rollback policy and the real Debian update lifecycle.

## Release payload integrity and private staging

`release_payload::verify` reads a bounded `manifest.cose`, authenticates it against an independently selected release public key, then requires exactly its signed regular files and their necessary directories. Missing/extra members, empty extra directories, special entries and symlinks in members or supplied directory ancestors fail. Every size/SHA-256 commitment is checked, and the binary must have an ELF64 little-endian amd64 executable header. The manifest is rechecked afterward. Required material files are authenticated as bytes; the separate material provider checks committed source, vendor contents and notices before installation work can consume them.

`stage` requires a fresh destination outside its source, checks available space including the control reserve, copies bounded contents into private files/directories, writes the authenticated manifest, verifies the complete copy and synchronizes files/directories. Existing destinations are preserved. Sources and destination ancestors remain under caller control during the operation; a verification result never authorizes later reads from mutable media. Failed staging is disposable and grants no installation authority. Executable permission is deliberately not granted by this copying layer.

`RuntimeProfile::matches` compares signed claims with a separately obtained candidate profile: exact version/target, core/readable schemas and migration registry hashes. The runtime exposes its actual compiled profile without opening node state. An updater must first authenticate/private-stage the candidate, then obtain its bounded report under an execution limit; it must separately check installed-data compatibility and persistent trust/sequence policy. These provider functions neither execute a candidate nor mutate installed trust, service selection or data.

Four portable tests cover round-trip staging, output preservation, integrity/missing/extra/self-listed/size failures, wrong authority/platform and compiled-profile mismatches. Unix adds linked member/directory/root/ancestor and mode checks. The runtime's Linux integration fixture covers a real ELF/profile; synthetic portable headers are never executed. The [material provider](../../deploy/materials/README.md) now prepares/verifies complete source/dependency/notices inputs with local fixtures; its actual packaged rebuild awaits CI. Durable anti-rollback/key rotation and real offline install/update/recovery remain B work.
