# Reference and archive guide

Reference/archive — not project canon. The [roadmap](../development/README.md) and the user’s latest applicable instructions govern current work.

| Material | Role |
| --- | --- |
| [Technical plan v1.0.0](technical-plan-1.0.0.md) | Historical architecture and sequencing snapshot; live choices are in the roadmap. |
| [Senior review of v1.0.0](review-2026-10-25.md) | Evidence of that design review and its then-current check counts; not proof about later revisions. |
| [Product history through v0.5.0](product-history-through-0.5.0.md) | Earlier status transitions, source audit and change records; old “proposed” or “governs” wording describes its date. |
| [ADR-0001](../decisions/ADR-0001-roadmap-lock.md) | Historical rationale for the initial lock; current selections live in DECISIONS and contracts. |
| Root master-spec / technical-proposal files | Compatibility redirects; no independent requirements. |
| Research, exported chats, future design notes, issues and PR discussions | Reference or proposals until adopted by an applicable user decision and reflected in current roadmap canon. |

Keep historical records labeled and dated; do not silently rewrite past decisions to appear current. A new proposal should identify its status, affected modules and intended canonical edits. Move accepted substance into the current roadmap rather than treating a link to the proposal as a second source of requirements. Code, tests and the work ledger provide execution evidence; licensing notices retain their legal effect.
