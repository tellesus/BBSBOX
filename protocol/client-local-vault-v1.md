# Local client vault v1

Implementation reference for the M00/M13 client persistence slice. [Client identity](../client/identity/src/local.rs) owns private key encoding and encryption. [Client vault](../client/vault/src/lib.rs) owns durable placement through the M02 single writer. Product authority remains in the [roadmap](../docs/development/README.md).

## Encrypted record

Use the recovery provider's fixed Argon2id v0x13 profile with 65,536 KiB memory, three iterations, one lane and a 32-byte output. Passphrases contain at least 15 characters and at most 1,024 UTF-8 bytes. An unlocked native session retains the derived key in zeroizing memory. Each checkpoint uses a fresh random 24-byte XChaCha20-Poly1305 nonce. A fresh vault uses a random 16-byte salt.

The canonical CBOR outer array contains six fields in this order.

1. Domain string `bbsbox.local-client/v1`.
2. Format integer `1`.
3. KDF profile integer `1`.
4. Salt byte string of length 16.
5. Nonce byte string of length 24.
6. Authenticated ciphertext, including the 16-byte tag.

The canonical encoding of the first five fields as an array is the authenticated data. Domain, version, KDF, lengths, size and canonical encoding are checked before expensive key derivation. An engine admits one KDF operation at a time. The existing `bbsbox.recovery-kit/v1` profile retains its bytes and meaning and uses the same encryption implementation.

## Local plaintext layout

Inside the authenticated ciphertext, concatenate the following fields.

| Field | Bytes |
| --- | --- |
| Local payload version `1` | 1 |
| Person root signing seed | 32 |
| Current device signing seed | 32 |
| Credential length, unsigned big endian | 2 |
| Exact verified C02 v2 device credential | Declared length, at most 512 |
| Recovery/rejoin flag, `0` or `1` | 1 |
| Positive checkpoint revision, unsigned big endian | 8 |
| Opaque client state | Remaining bytes, at most 8 MiB |

The device secret must match the signed device credential and its person root. The SQLite revision must match the encrypted revision, which cannot exceed the signed 64-bit SQLite range. Root control incarnations are regenerated on unlock. Ordinary restart preserves the device credential and saved client state. Client encryption adapters must checkpoint their ratchets, counters and queued ciphertext together before publishing output.

## Durable operations

One M02 writer holds the client database lock. Its `client-vault` migration stores one encrypted record and public revision. Setup inserts only into an uninitialized vault. A failed setup may be retried against an empty initialized database. Existing identities require unlock and are preserved on wrong passphrases, malformed records and setup retries.

State checkpoints compare the expected revision and update the encrypted record and revision in one transaction. In-memory state advances after commit succeeds. A stale or uncertain caller reconciles with the durable revision before continuing. The native adapter runs KDF and storage operations on blocking workers and reports busy state without waiting in UI status calls.

## Backup recovery

The supported backup API exports a recovery kit from the person root and explicitly supplied receive-side state. Local device seeds and the complete local checkpoint are excluded from that export. Import preserves the person identity, creates a fresh device, stores only the supplied receive-side state and sets the persistent rejoin flag. A normal restart retains that flag. M13 must obtain and validate a fresh owner-authorized MLS join before enabling private sending for a recovered group.

Tests cover an actual kit generated by the preceding implementation, checkpoint/kit domain rejection, normal restart, failed and stale saves, wrong passphrases, single-writer exclusion and recovery followed by restart. The native WebView fixture exercises these paths with actual encrypted files.
